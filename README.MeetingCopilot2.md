# MeetingCopilot 2.0（二次开发说明）

面试实时提词 + **接地气的 RAG**：转写面试官提问 → 中文问题提取 → 依据你**真实的项目资料**生成第一人称、可直接念的中文回答。

核心目标是**不瞎编**。为此有两套机制：检索只把"有据可查"的片段喂给模型，以及每条片段都带**事实边界档位**，明确区分"已证实 / 简历包装值 / 只是规划"。

> 本项目基于 [MeetingCopilot](https://github.com/JWM0203/MeetingCopilot)（Apache-2.0）二次开发。
> 原始版权与许可见 [LICENSE](LICENSE)，上游原始说明见 [README.md](README.md) 与 [README.zh-CN.md](README.zh-CN.md)。
> 二次开发部分：RAG 引擎、事实边界标注、防幻觉提示词层、中文界面接线。

## 2. 快速开始

```powershell
cd D:\MeetingCopilot2.0
npm install                     # 首次
npm run build
npm start                       # 或直接运行 node_modules\electron\dist\electron.exe .
```

### 3 步配好

1. **配 LLM 与转写**（与用原版一样）
   Settings → LLM：选「DeepSeek V4.1-Flash（deepseek-flash）」，填 DeepSeek Key
   Settings → STT：阿里云 `fun-asr-realtime` + DashScope Key

2. **导入资料**（主窗口顶部三个槽位，**每槽都可一次多选多份**）

   | 按钮 | 槽位 | 放什么 |
   |---|---|---|
   | 📄 简历 | `resume` | 你的简历 |
   | 📁 项目 | `project` | 项目讲稿、面试问答速查、项目手册（可多份） |
   | 📋 JD | `jd` | 目标岗位 JD |

   支持 `.md` / `.txt` / `.docx` / `.pdf`。点按钮 → 文件框**可一次多选**；
   槽内已有内容时按钮会展开清单，可**逐份移除**或继续追加；按钮上的角标显示份数。
   扫描版 PDF 会逐文件报错（没有文本层，需先 OCR）。

3. **配 embedding 并建索引**
   Settings → 「检索增强 / RAG」→ 预设「阿里云百炼 text-embedding-v3」
   → 填 **同一个 DashScope Key**（与转写共用，不用另注册）
   → 点「测试 embedding 连通性」确认成功
   → 点「重建索引」：会**逐份**索引三个槽里的全部文档，并显示每份的进度

> ⚠️ 只导入不建索引，检索不会生效（会自动退回"整份资料直塞"的老方式）。
> 界面在索引未就绪时不会发检索请求，避免"每一题都只得到兜底话术"。

### 为什么分三个槽

真实面试要同时带上**简历**（我是谁）、**项目资料**（我做过什么，通常好几份讲稿）
和**岗位 JD**（往哪儿贴）。原来只有"简历 + JD"两个槽，项目讲稿只能塞进简历槽，
和真正的简历混在一起互相稀释检索结果。分槽之后：

- 检索可以按槽位过滤（问"岗位要求"时优先查 JD 槽）；
- 界面能显示"这条依据来自哪份资料的哪一段"；
- 建索引逐份进行，某一份失败不会影响其它文档。

## 3. 为什么 embedding 走外部 API

NexQ 的 RAG 用本地 Ollama 做 embedding，优点是离线免费，代价是要装约 1GB 运行时 + 模型、冷启动 2–5 秒，而且中文效果一般。

本项目改为调用 **OpenAI 兼容的 `/v1/embeddings`**：

- 建索引是**一次性离线任务**：25 万字语料约 ¥0.05；
- 运行时每次提问**只调一次** query embedding（约 0.3 秒）；
- 换服务只改 baseUrl + model，不动代码；
- 不引入任何原生模块（不用 better-sqlite3 / Ollama）。

内置预设：阿里云百炼 `text-embedding-v3`（推荐）、硅基流动 `BAAI/bge-m3`、OpenAI `text-embedding-3-small`、自定义任意兼容端点。

## 4. 防瞎编是怎么做到的（四层）

检索只能决定"哪些句子**有可能**被说出来"，它**无法判断真假**。所以真正的防线有四层，其中三层在检索之外。

### L1 入库标注事实边界（`electron/rag/factlevel.ts`）

每个片段入库时打一个档位，注入 prompt 时随片段一起带上，并附对应处理指令：

| 档位 | 含义 | 送给模型的指令 |
|---|---|---|
| `verified` 已证实 | 能指到文件/模块/实测 | 可正常陈述，作为真实经历讲 |
| `claimed` 目标值/待确认 | 简历里的包装数字，缺实测支撑 | **绝不能说成既成事实**；被追问要如实说明这是目标或口径 |
| `unverified` 未证实 | 资料里的"预计/规划" | 只能作为计划讲，不能当成已完成 |

判定是**确定性规则**（无 LLM，索引可复现、可人工核对）。两条关键设计：

- **人工标记优先**：你的资料里本来就有【项目】/【通用】/【边界】标注，这类信息比任何正则都可靠；
- **不是"有数字就算风险"**：实测若把任意数字都判为高危，真实讲稿的待确认占比会到 **91.7%**、简历手册 **100%**，徽章满屏橙色 → 用户脱敏 → 真正危险的包装数字反而被淹没。现在只把**质量指标**（准确率/F1/召回/QPS/延迟…）与**带计量单位的数字**当风险，并把代码块排除（代码里的常量是实现事实，不是业绩声明）。

调优后实测（4 份真实求职资料，25.8 万字）：

| 文档 | 待确认占比 |
|---|---|
| 面试问答速查 | 20.7% |
| 经纬恒润讲稿（14.6 万字） | 32.5% |
| 得物 EchoMind 问答 | 43.6% |
| 海洋遥感手册 | 20.2% |
| **合计** | **28.7%**（健康区间 10%–50%） |

### L2 生成只依据片段（`electron/llm/prompts.ts`）

片段以 `[S1] [S2]` 编号 + 来源 + 档位注入，并给模型**可执行**的约束（而不是"不要编造"这种空话）：

- 指不到来源的事实句，**一句都不要写出来**
- `claimed` 的数字**原样引用，禁止换算、取整、外推、四舍五入**
- `unverified` 只能讲成计划或预期
- 资料里没有的能力、公司、项目、数字，**一律不要补**

### L3 信息不足时不调用模型（`electron/main.ts`）

`retrieve()` 用**原始余弦**判定置信度（不是 RRF 归一化分数——那种分数永远接近 1，阈值筛不掉任何东西）：

- `topScore < minScore` → **不调用 LLM**，直接返回 `buildFallbackAnswer()` 的兜底话术。
  不让模型生成，是唯一 100% 有效的防瞎编手段。
- `topScore === 0` → 证据清空。此时只有关键词噪声、没有语义依据，留着会被调用方误当证据。

### L4 界面可验证（`src/components/AnswerSession.tsx` + `shared/citationAudit.ts`）

- 每条回答下方「依据 N 条 · 最高余弦 · 检索耗时」，可展开看每条 `[S#] 来源 · 档位 · 分数`；
- 走了兜底话术时显示琥珀色横幅「**本次未调用大模型（资料中未找到依据）**」；
- `claimed` 档位用橙色徽章，悬浮提示"简历口径，缺实测支撑，被追问时需如实说明"；
- **引用覆盖率审计**（纯规则，不额外调模型）：
  - `引用覆盖率 67%（2/3 个事实句标了出处）`
  - 列出**含数字或具体指称、却没标来源**的句子 —— 这是唯一能"当场自查"的一环；
  - 引用了不存在的编号（`[S9]`）单独告警：那是模型**编造来源**的典型形态；
  - 泛化陈述（"我比较注重沟通"）不计入统计，避免满屏告警导致用户脱敏。

> ⚠️ **资料本身要诚实。** 你的资料里有一处自承认的问题：简历写的
> 「500 条 / Accuracy 91.3% / Macro-F1 0.89 / RAG 88.7%」在仓库中没有支撑，
> 真实 baseline 只有 11 条样本、Accuracy 81.8%。这类包装数字与真实数字在向量空间里
> **语义高度接近，纯检索区分不了**——所以才需要 L1 把它标出来。请确保这类边界说明
> 就在被索引的资料里（`claimed` 档位正是为它们准备的）。

## 5. 中文检索：为什么不用 FTS5

NexQ 用 SQLite FTS5 做关键词分支。实测它在本项目场景下是**失效**的：

| 查询词 | FTS5 默认分词器 | `tokenize='trigram'` |
|---|---|---|
| 海洋遥感 | **0 命中** | 命中 |
| 知识服务平台 | **0 命中** | 命中 |
| 多智能体 | **0 命中** | 命中 |

原因是 FTS5 默认分词器按空格切词，而中文没有空格，整段中文被当成一个巨大 token。所以中文场景下它的"混合检索"实际只有向量那一半在工作。

本项目做法：**向量为主 + 字符 bigram 关键词加分**（中文无需分词器），并对专有名词/指标（`91.3%`、`FTS5`、`RRF`）给精确命中加分。关键词权重上限 0.15，不喧宾夺主。

另外：**向量检索是全量内存暴力余弦**。640 段 × 1024 维 ≈ 2.6MB，毫秒级，不需要 ANN 索引。

## 6. 目录结构

```

  store.ts       JSON + 内存向量（原子落盘、模型/维度校验）
  search.ts      余弦 + 中文 bigram + 邻接扩展 + 低置信判定
  indexer.ts     索引流程（切块→标注→向量→入库，含完整性质检）
  index.ts       门面 RagService

src/components/RagSettingsPanel.tsx RAG 设置面板（全中文）
src/components/RagEvidenceView.tsx  依据区块 / 档位徽章 / 引用覆盖率
shared/sessionMaterial.ts           三槽多文档的读写与旧格式迁移（唯一解释点）
shared/ragDefaults.ts               预设与默认值（主进程与渲染进程单一事实源）
shared/citationAudit.ts             引用覆盖率审计（哪些事实句没出处）
shared/readiness.ts                 面试前自检（写好了，界面入口待接）
test/*.spec.ts                      603 个测试，含 76 个对抗性用例
tools/rag-corpus-stats.mts          真实语料体检（切块质量 + 档位分布）
tools/rag-offline-check.mts         离线链路验证（无需 API Key）
```

```powershell
# 离线链路验证（假向量，不需要 Key）

# 真实 embedding 端到端 + 阈值校准（需要真 Key）

npx vitest run test/rag-e2e-live.spec.ts
```

### ⚠️ 必须校准 `minScore`

默认 `0.45` 是**初始估值，没有实测依据**。中文同域文本的余弦基线常在 0.3–0.6，不同 embedding 模型的尺度也不一样，所以这个值必须用你自己的语料校准：

```powershell
$env:DASHSCOPE_API_KEY='sk-xxx'
$env:RAG_CORPUS='D:\你的讲稿.md'
npx vitest run test/rag-e2e-live.spec.ts
```

脚本会输出"相关问题最低分"与"无关问题最高分"，给出建议阈值，并写入 `rag-calibration.json`。

- 两者**分得开**：取中点作为 `minScore`；
- 两者**重叠**（中文同域文本很可能如此）：单一绝对阈值本质失效，此时应把阈值设得保守一些，把判断交给 L2 的引用约束与 L4 的界面标注。

## 8. 已知限制

- **检索结果只存内存**：重启后旧回答的「依据」区块消失，当次会话内完全可用。
- **本机未安装 Electron 二进制时**，5 个测试套件会在 import 阶段失败（`Electron failed to install correctly`）。本项目已从同版本安装复制过一份；重装依赖后如再出现，执行 `node node_modules/electron/install.js`。
- **`ELECTRON_RUN_AS_NODE` 环境变量**会让 Electron 以纯 Node 模式启动并立即崩溃（表现为"双击没反应"）。正常桌面环境不会设置它；若在自动化脚本里启动，请先清除该变量。
- **扫描件 PDF 无文本层**：解析结果为空，界面会提示，需先 OCR。
- **无 rerank 模型**：检索只做余弦 + 关键词加权。语料继续变大（>50 万字）后可考虑加一层精排。
- **不做跨会议记忆**：每次问答独立检索，不维护"已问过什么"的跨轮台账（原版的滚动 memo 仍保留，用于会话内一致性）。
